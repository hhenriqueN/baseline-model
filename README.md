# Baseline model -- autonomous FlightGear landing (Cessna 172P)

Insper Capstone project (2026). The goal is to teach a neural-network autopilot to
**land a Cessna 172P in the FlightGear simulator** by imitating human-flown
demonstrations (behavioral cloning), following the approach of
Baomar & Bentley (2021), *Autonomous flight cycles and extreme landings of airliners
beyond the current limits and capabilities using artificial neural networks*.

The repository contains the full chain, from raw simulator logs to a live controller:

1. **Data pipeline** (`pipeline/`, `scripts/`) -- ingests FlightGear CSV logs recorded
   at ~60 Hz, audits and cleans them, splits the full traffic circuit into landing
   episodes, resamples to 10 Hz, labels flight phases with a landing state machine
   (final approach, flare, touchdown, rollout, ...) and builds the model features.
2. **Training** (`training/`) -- two small PyTorch MLPs trained offline with
   leave-one-session-out cross-validation, then a final fit on all valid flights:
   - **lateral** network -> aileron + rudder
   - **longitudinal** network -> elevator + throttle
3. **Controller** (`controller/`) -- a real-time 10 Hz closed-loop controller that
   talks to FlightGear, recomputes the features online, runs the two frozen networks
   in the airborne phases and hands over to a deterministic ground controller after
   touchdown, with safety limits on every command.

## Quick start

```bash
git clone https://github.com/hhenriqueN/baseline-model.git
cd baseline-model
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# rebuild the derived datasets from data/raw/ (see "Reproducing everything" below),
# then run the tests
python3 -m pytest tests/ -v

# closed-loop test against the mock simulator (no FlightGear required)
python3 -m controller.mock_flightgear --help
```

Developed with Python 3.13, PyTorch 2.x, pandas 2.x.

## Overview of results and design notes

Data pipeline + offline behavioral-cloning baseline for the two airborne control
MLPs (lateral: aileron/rudder; longitudinal: elevator/throttle). See
`reports/training_report.md` for the full report (root-cause analysis, phase-machine
correction, cross-validation and final-training results, limitations) and
`reports/paper_analysis.md` for the Baomar & Bentley (2021) paper review.

A real-time FlightGear closed-loop controller (`controller/`) is also implemented,
loading the two frozen checkpoints above and driving the aircraft at 10 Hz. See
`reports/controller_report.md` for the full report: exact launch command, initial
conditions, communication protocol, elevator/trim handling, test results, a known
one-time macOS permission blocker preventing a fully live FlightGear run in this
session, and the mock-FlightGear closed-loop validation performed instead.

```bash
PYTHONUNBUFFERED=1 python3 -m controller.run --launch-flightgear --scenario nominal --mode shadow
PYTHONUNBUFFERED=1 python3 -m controller.run --launch-flightgear --scenario nominal --mode active
```

Deterministic rollout/go-around ground control is implemented as a minimal
deterministic controller (`controller/rollout_controller.py`); full actuator
rate-limit tuning and go-around logic remain future work (see the controller report).

## What a future real-time controller must load

Everything a closed-loop controller needs is consolidated in
**`models/model_manifest.json`**, generated by `training/build_model_manifest.py`.
For each network (`lateral`, `longitudinal`) it lists:

- `checkpoint_path` -- PyTorch `state_dict` (`models/<network>/final/checkpoint.pt`),
  loadable via `training.models.{LateralMLP,LongitudinalMLP}().load_state_dict(torch.load(...))`.
- `feature_order` -- the exact ordered list of input variables the checkpoint
  expects (11 for lateral, 12 for longitudinal, spec sections 15-16). The
  controller must assemble inputs in exactly this order.
- `input_normalization` -- which variables to z-score (train-set mean/std, clip to
  `[clip_min, clip_max]`) and which to pass through unchanged
  (`heading_error_sin/cos`, `flaps_state_norm`, `flare_flag`), taken from
  `data/scalers/final_all_valid/scaler_final_all_valid.json`.
- `label_order` + `output_saturation` -- output names and the `[lo, hi]` range each
  must be clamped to before being sent to the simulator (labels themselves are
  never normalized).
- `eligible_training_phases` / `excluded_phases_from_training` -- documents which
  Flight-Manager phases these networks were trained for (final approach, flare,
  candidate touchdown) and which they must never be asked to control
  (touchdown-confirmed, bounce, rollout, complete, go-around -- those need a
  deterministic ground controller, not this baseline).

Do not load raw checkpoints without also applying the manifest's normalization --
predictions will be meaningless on raw-unit inputs.

## Repository layout

```
data/            raw (immutable) -> validated -> processed/10hz -> features -> splits/scalers
pipeline/        reusable pipeline code (io, resampling, runway geometry, landing
                 state machine, feature engineering, splits, scalers, checks)
scripts/         01..11, run in order to rebuild data/ from data/raw/ (never edits data/raw/)
training/        PyTorch dataset/model/training/reporting code for the two MLPs
controller/      real-time FlightGear closed-loop controller (launch, telemetry/command
                 I/O, online features, causal Flight Manager, rollout controller, safety)
models/          trained checkpoints + configs (per-fold and final) + model_manifest.json
reports/         paper_analysis.md, training_report.md, controller_report.md, phase_validation/, training/
runs/            per-run controller logs (launch command, telemetry, predictions, summary)
tests/           pytest: phase-machine, dataset/split integrity, model, controller tests (286 tests)
```

## Reproducing everything

```bash
# 1. rebuild the datasets (also regenerates the phase-machine correction)
for s in 01_ingest 02_audit 03_segment_circuit 04_build_episodes 05_build_validated \
         06_resample 07_detect_transients_and_phases 08_build_features \
         08b_build_processed_variants 09_build_splits_and_scalers 10_apply_scalers \
         11_build_reports; do python3 scripts/${s}.py; done

# 2. tests (must pass before any training, per spec section 23)
python3 -m pytest tests/ -v

# 3. cross-validation training (13 LOSO folds x 2 networks)
python3 -m training.run_cv
python3 -m training.make_reports

# 4. final training on all valid demonstrations + manifest
python3 -m training.run_final
python3 -m training.build_model_manifest
```

Raw files in `data/raw/` are immutable and never modified by any script. The
familiarization flight `voo-inicio-teste.csv` is preserved but excluded from every
downstream dataset, fold, and scaler.
